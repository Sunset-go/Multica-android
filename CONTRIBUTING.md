# Contributing

Thank you for your interest in contributing to Multica Android App. This
repository is a self-contained Expo / React Native client extracted from the
[Multica](https://github.com/multica-ai/multica) monorepo.

## Quick start

```bash
pnpm install
pnpm dev:mobile              # Metro (local backend)
pnpm dev:mobile:staging      # Metro (staging backend)
```

For a device build or release APK, see [`apps/mobile/README.md`](./apps/mobile/README.md).

## Environment

- Node.js 20+
- pnpm 10 (`packageManager: pnpm@10.28.2` pinned in `package.json`)
- iOS dev requires Xcode; Android dev requires the Android SDK

## Before opening a PR

Run the CI-equivalent checks locally:

```bash
pnpm typecheck
pnpm lint
pnpm test
```

All three must pass. `apps/mobile/CLAUDE.md` covers the deeper project
conventions — RNR waterfall, real-time subscriptions, APK builds, and
lessons learned from prior work.

## Project structure

```
apps/mobile/           # Expo app (iOS + Android)
packages/core/         # @multica/core: shared business logic & types
packages/tsconfig/     # shared TS configs
packages/eslint-config/# shared ESLint configs
```

Cross-package imports must go through `packages/core/package.json`'s
`exports` whitelist — deep relative paths are not allowed.

## Coding style

- **TypeScript strict mode** with `noUnusedLocals`, `noUnusedParameters`,
  `noImplicitReturns`, `noUncheckedIndexedAccess`.
- **Tailwind v4 + NativeWind** semantic tokens only (`bg-background`,
  `text-muted-fore`, `text-primary`, ...). No hardcoded hex values in new
  code.
- **UI waterfall**: iOS native API > React Native Reusables (RNR) > stop and
  ask. Don't write a new generic UI primitive for one call site.
- **Never `as T` cast** on API responses — always go through
  `fetchValidated(path, schema, fallback)` with a Zod schema from
  `packages/core/api/schemas.ts`.
- **Never import** from `packages/core/<feature>/ws-updaters.ts` on the
  mobile side — implement the mirror in
  `apps/mobile/data/realtime/<feature>-ws-updaters.ts`.
- **Never hand-modify** `node_modules/`, `dist/`, `build/`, `coverage/`,
  `*.tsbuildinfo`, `*.apk`, `apps/mobile/android/` — these are build
  artifacts or generated by `expo prebuild`.
- **Never edit `pnpm-lock.yaml`** unless a real dependency is added.
- **Never hardcode** API keys / tokens / passwords — secrets only via
  `expo-secure-store` or env vars. `.env.example` is placeholders only.
- **Never commit** to `main` directly; use a feature branch.
- **Never force-push** `main`.

## Commit messages

Conventional Commits:

```
feat(inbox): add swipe-to-archive with haptic feedback
fix(api): forward TanStack Query signal through listInbox
chore(deps): bump expo to 54.5.0
```

## Pull requests

1. Link the scope (`apps/mobile/**` or `packages/core/**`) so CI can pick
   the right pipeline.
2. Include before/after screenshots for UI changes (formSheet / Modal /
   keyboard layouts).
3. For changes that span mobile and web, describe cross-client verification
   results (web edit → mobile sync within 500 ms, etc.).
4. If you touched a Tier C legacy component, note any hardcoded hex you
   saw as a follow-up — don't rewrite it in this PR.

## Release

- Tag pushes matching `v*.*.*` (e.g. `v0.2.8`) trigger
  [`.github/workflows/android-release.yml`](.github/workflows/android-release.yml)
  which bumps version, builds arm64 + universal APKs, and publishes to
  GitHub Releases.
- The workflow also supports `workflow_dispatch` with a `version` input for
  manual builds.

## Reporting issues

- Use the GitHub Issues template if available.
- Repro steps for mobile behavior should include:
  - Device (iOS version / Android version, physical vs simulator)
  - Metro log tail
  - Backend URL (`local` / `staging` / `prod`)
  - Minimal repro (screenshots, screen recordings, or a small diff)

## Security

Do not open a public issue with a security concern. Contact the maintainer
privately via email and we'll work with you to coordinate disclosure.
